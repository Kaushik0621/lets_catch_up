Owned the AI layer of Chumley, an internal marketing-and-operations platform: an analytics chatbot over 78 tools, an AI pilot that plans Google Ads changes through a guarded write path, and the forecasting models underneath them. The changes that pilot plans now drive 30% of new customer generation.

Agentic AITool-Calling LLMsForecastingData Correctness
  • Built the analytics chatbot at the centre of the platform, on a custom tool-calling loop with no framework. Its 78 tools cover the system end to end — campaigns, spend, leads, jobs, Salesforce records, forecasts — so a question about any part of the business has a tool that can answer it rather than a model inferring it from whatever happened to be in context.
  • Wrote the orchestration layer that works out which of those tools a question actually needs, and the agentic loop around it: the agent calls a tool, reads what came back, and decides whether that answers the question or whether it needs to go again — chaining calls until the answer is genuinely resolved instead of stopping at the first plausible-looking result.
  • Built a separate presentation layer so the reply is shaped by what was asked. The same underlying result arrives as a table, a comparison, a trend or a short narrative depending on the question, instead of every answer being returned as the same wall of prose.
  • Put an AI pilot on top of it that plans the Google Ads work itself — reading current state, proposing a coherent multi-change plan for human review, and handing it to the one guarded write path. The changes it plans now drive 30% of all new customer generation.
  • Built a per-campaign investigator alongside them that produces an entity-level to-do list and then tracks whether each item was actually actioned, so a recommendation is followed through rather than filed.
  • Built the lead forecasting model the business plans against — how many customer enquiries each campaign will return over the coming period, published as a conformal band rather than a single number, so budget is committed against a range the model can defend instead of a point estimate nobody can audit.
  • Laid the groundwork for spend prediction: a Poisson spend-to-leads model that estimates what each additional pound on a campaign actually returns, so spend can be planned against a forecast rather than reallocated from last month’s figures.
  • Modelled what a lead is worth, not just how many arrive — a hurdle logistic plus Gamma GLM with empirical-Bayes effects that separates whether a job converts from what it bills, cutting median holdout error 20% and letting campaigns be ranked on expected revenue. Alongside it, quantile bands for how long a job takes to complete, for capacity planning.
  • Cut what the agents cost to run by measuring rather than guessing: a deterministic lexical tool router that kept full recall on a 17-case suite while cutting prompt tokens 48%, and a restructured investigator context that cut its input tokens a further 62%.
  • Made the agents safe by construction. Deterministic code decides which changes are possible and computes every number; the model may only choose from that list, order it and explain it. No agent holds a write path of its own, so a wrong answer costs a weaker suggestion rather than a corrupted ad account.
  • Traced bad numbers back to their source and fixed them: campaign geography was being guessed from campaign names instead of real targeting data, a nightly mirror was drifting with nothing to catch it, and a feature flag matched by string was wrong for 61 of 64 cases. Put the reliability layer in behind it — a structured error contract replacing endpoints that returned HTTP 200 with the failure buried in the body, an incident ledger, and alerting deduplicated and segmented by impact.

RAG & Vector SearchInsurance AnalyticsFraud DetectionPipeline Automation
  • Built a RAG pipeline over insurance claim and incident records — documents chunked, embedded and held in a vector database, retrieved by semantic search — so a claims handler could ask a question in plain English and get an answer with the source passages it rests on attached.
  • Used it for pattern recognition across claim histories, surfacing which incidents cluster by season, site and cause. National Rail’s winter weather and track incidents and the North Sea rigs’ own seasonal profile both read as recurring, predictable exposure rather than a series of unrelated events, which let underwriting anticipate the peak instead of reacting to it.
  • Applied the same patterns to fraud prevention: claims that sit outside the established seasonal, geographic and causal profile are flagged for investigation, so assessors review the genuine outliers instead of sampling the whole book.
  • Made cause explainable. Given a new incident, the pipeline retrieves its closest historical matches and returns the contributing factors those cases shared, with the records cited — turning “why did this happen” from a manual file review into a question with a traceable answer.
  • Automated the pipeline end to end with webhooks triggering ingestion, embedding and indexing as new claims land, behind data guardrails that validate each record on the way in and quarantine what fails rather than letting a malformed batch silently degrade retrieval.
